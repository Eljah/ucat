# Архитектура промышленной версии «Помощь активисту»

## Прототип vs следующий этап

Текущий MVP — единый Java 17-процесс, JDK `HttpServer`, JSON-файл, JavaScript + Leaflet, ручная геопривязка, экспериментальные HTML-адаптеры. Такой стек выбран специально для запуска в один JAR и проверки пользовательской гипотезы. **Это не полнофункциональный городской мониторинг.**

После проверки UX предлагается многомодульный Maven/Java 17+ проект на Spring Boot + PostgreSQL/PostGIS, где у каждого источника свой адаптер, контракт и тестовые HTML/PDF-фикстуры.

```text
pomosh-aktivistu/ (Maven modules)
  api/                 Spring Boot REST + authentication + OpenAPI
  domain/              Project, SourceDocument, Evidence, Territory, Alert
  ingestion-core/      Connector SPI, scheduler, retries, fetch cache, versions
  connectors/
    dispute/           discuss notices, exposure dates, proposal deadlines
    docskzn/           municipal publication issues and announcements
    pravo/             legal acts incl. PDF attachments
    kzn-planning/      planning registry and project decisions
    dvor/              address lists and residents' meeting schedules
    data-kzn/          CSV/XLSX/GeoJSON from city open data portal
    eis/               official delivery/RSS if integration permitted
  document-analysis/   PDFBox/Tika for text and attachments, OCR as fallback
  geography/           Russian address NLP; FIAS/GAR; cadastral matching; JTS
  matching/            PostGIS intersect/distance + uncertainty and review queue
  notification/        Telegram, email, web/push; idempotence and digests
  web/                 Leaflet UI and citizen action workflow
  infra/               Flyway, Docker Compose, observability, backup
```

Базовая модель данных должна хранить **происхождение каждого факта**: URL, хеш первоисточника, версия публикации, страница или фрагмент документа. Без этого теряется возможность проверить, откуда получен вывод «затронута ваша территория».

## Пространственное сопоставление

База хранит полигон активиста и геометрию объекта. Если точная геометрия работ известна, сравнение должно выглядеть так:

```sql
SELECT w.id, p.id
FROM watch_area w
JOIN project_location p ON ST_Intersects(w.geom4326, p.geom4326)
WHERE p.precision = 'EXACT';
```

Используется `ST_Intersects` из PostGIS, с индексами `GiST`. Для адресных точек низкой точности — отдельная оценка в метрах через `geography`, `ST_DWithin` и порог по классу объекта. **Никогда не повышать статус приблизительной геокодировки до точного совпадения.**

Для длинных дорожных объектов нужно сопоставлять `LineString`/коридор работ, а не среднюю точку; для кадастровых номеров — доставать контур участка из авторизованного/законного набора, отдельно проверяя его актуальность.

Для публичной службы геокодирования нужно договориться о допустимой нагрузке и условиях. Массовое использование бесплатного `nominatim.openstreetmap.org` не планируется; при необходимости ставить собственный Nominatim или использовать лицензированный геокодер с кешированием.

## Как связывать несколько документов в один проект

**Не объединять только по одинаковому адресу.** На одной улице могут одновременно выполнять реконструкцию дороги, ремонт водопровода и благоустройство двора.

- Сопоставлять официальные номера постановлений, номера ППТ/ПМТ, кадастровые номера, объект строительства, номер закупки, контракта.
- Использовать пространственное пересечение + похожее название + виды работ, но отмечать связь как вероятную, если нет общего идентификатора.
- Хранить историю стадий с датами, предыдущими документами и ссылкой на первичное решение о подготовке.
- При появлении поправки к проекту считать это *новой версией* и сравнивать затронутые положения, а не просто сообщать «вновь опубликован старый документ».

## Что считать оповещением с высокой полезностью

1. Появилось постановление **о подготовке** проекта: короткое сообщение, объект/территория и возможные действия (посмотреть задание, запросить материалы).
2. Появилось оповещение **о начале обсуждения**: первоисточник, подтверждённая дата начала, порядок и сроки предложений, если извлечены надёжно.
3. В проекте сменили границы или назначение участка: diff документов/чертежей, а не одна фраза «изменения».
4. Появилась закупка **проектирования**: техническое задание часто информативнее позднего контракта на строительство.
5. Участок точно совпадает с полигоном пользователя: персональный alert; возможное совпадение — запрос на проверку; неизвестная география — сводка важных публикаций без ложного отрицания.

Система не должна автоматически писать обращение «от имени активиста» и тем более направлять его куда-либо без отдельного подтверждения. Нужны проекты текстов, где каждое замечание подкреплено документом и конкретным параметром проекта.

## Технический мониторинг достоверности

Помимо числа найденных документов, поддерживать метрики: `lastSuccessfulPoll`, `sourceLag`, `parsedDocumentShare`, `geolocatedShare`, `unlocatedHighPriority`, `deadlineKnownShare`, `duplicateRate`, `connectorErrors`. При падении коннектора слать **отдельное** оповещение «источник не проверялся с ...». Статус источника никогда не приравнивать к отсутствию новых событий.

## Этапы после MVP и критерии готовности

**Этап A (сбор).** Реальные, воспроизводимые адаптеры 4 первоисточников (DISPUTE, PRAVO, DOCSKZN, GRAD). Минимум 20 архивных фикстур с позитивными/негативными случаями. Стабильные `externalId`, хеши и даты.

**Этап B (география).** Получение адресов, номеров участков, классификатор точных и сомнительных соответствий, ручная верификация карты. Важный тест: документ о фрагменте длинной улицы не должен автоматически «накрыть» всю улицу.

**Этап C (раннее уведомление).** Telegram digest, источники с разной частотой, правильная работа после выключения/восстановления сервера, отсутствие повторных уведомлений.

**Этап D (полнота).** ЕИС, `data.kzn.ru`, «Наш двор», ремонтные перечни; извлечение таблиц/PDF и постепенная история проектов. Проверить два разных года по историческим данным на пропущенные объявления.

**Этап E (обратная связь).** Вкладка с замечаниями, сроками, официальным порядком участия, версиями проекта и подтверждением подачи — без автоматической отправки без согласия.

## Риски

1. **Ложное спокойствие:** главный риск — не ошибка сопоставления, а незаметное падение парсера или игнорирование событий без геометрии.
2. **Сроки:** не подменять «первую дату обнаружения» правовым сроком.
3. **Право участия:** для разных типов обсуждений и лиц действуют разные процедуры, некоторые проекты проходят без слушаний.
4. **Нагрузка и доступ:** официальный сайт не обязан терпеть постоянный HTML-скрейпинг. Проверять API, правила, согласованную частоту.
5. **Обновления:** конфиденциальные координаты интересов активиста, заметки и каналы связи требуют авторизации и шифрования при развёртывании публичного сервиса.

## Модуль анализа потенциальных недостатков проектных решений (дальнейшее развитие)

Приложение должно не только извещать о документе, но и помогать сформулировать **что именно проверить**. Это пока не автоматическое обнаружение нарушений норм. Предлагается генерация проверочного списка по типу проекта:

| Тип решения | Что предложить активисту проверить |
|---|---|
| Реконструкция улицы | непрерывность тротуаров, доступность переходов, пути к остановкам, деревья и тень, безопасность поворотов, ливневая канализация |
| Благоустройство двора | существующие деревья, пешеходные связи, безбарьерный путь, машиноместа, детские зоны, способ отведения воды, участие собственников |
| Изменение ПЗЗ/ППТ | функциональные зоны, красные линии, границы зелёных участков, предполагаемая плотность, доступ к объектам общего пользования |
| Строительство объекта | подъезды строительной техники, шум, перекрытия, пожарные проезды, инженерные сети, сохранность соседних участков |
| Капремонт | исходное состояние, объём работ, сроки, влияние на доступность, приемка |

Каждый пункт показывать в форме *вопроса к документу*, а не утверждения о выявленном недостатке. При наличии геометрий, чертежей и нормативных параметров можно в будущем рассчитывать измеримые показатели и давать ссылки на конкретные страницы документации, но только после проверки точности извлечения.

Отдельная задача — эффекты вне полигона пользователя: перекрытая дорога вне границы может влиять на доступ к району, а стройка рядом с ним — на шум/транспорт. В будущем нужны *буфер интереса* и *модель зоны воздействия* наряду со строгим `ST_Intersects`.
